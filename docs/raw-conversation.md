# 이게 중요한 이유가 있어.

웨딩은 일반 쇼핑과 굉장히 다르거든.

사람이 보통 이렇게 검색하지 않아.

> `A라인 드레스 강남 200만원`

오히려

> “이런 느낌인데…”

하면서 **사진을 보여줘.**

즉 query 자체가 텍스트가 아니라 **이미지 집합**인 시장이야.

현재 LLM/VLM이 정말 좋아진 영역이 정확히 이것이고.

그래서 이건 그냥

> AI 웨딩 플래너

보다 훨씬 날카로운 wedge야.

**Wedding visual search engine.**

# AI 기반 웨딩 취향 탐색 서비스 기획 초안

## 1. 문제 정의

한국에서 스드메를 알아보는 과정은 여전히 매우 비효율적이다.

특히 사용자가 원하는 스타일을 찾는 방법이 대체로 다음에 의존한다.

- 인스타그램에서 직접 검색하고 저장하기
- 웨딩플래너의 추천 받기
- 웨딩 커뮤니티 후기 탐색하기
- 업체별 포트폴리오를 일일이 비교하기

문제는 정보가 부족한 것이 아니다.

오히려 정보는 너무 많지만,

> **“내가 어떤 스타일을 좋아하는지”**
>  
> **“내 취향과 실제 업체를 어떻게 연결할지”**

를 도와주는 도구가 부족하다.

현재 대부분의 웨딩 서비스는 `업체 → 상품 → 가격 → 상담` 구조다.

하지만 실제 사용자의 탐색은 오히려

`사진 → 느낌 → 취향 → 비슷한 업체`

에 가깝다.

---

## 2. 핵심 가설

웨딩 소비자는 업체명이나 상품명보다 **시각적 취향을 먼저 가지고 있다.**

하지만 그 취향을 언어로 정확히 설명하기 어렵다.

예를 들어 사용자는

- “자연광 느낌”
- “너무 화려하지 않은 것”
- “깨끗한 느낌”
- “이런 사진 같은 분위기”

정도로만 표현한다.

따라서 AI의 역할은 웨딩플래너를 대체하는 것이 아니라,

> **사용자가 가진 이미지 기반 취향을 구조화하고,
> 그 취향을 실제 선택 가능한 업체와 연결하는 것**

이다.

---

## 3. 제품 한 줄 정의

> **업체를 찾기 전에, 내가 원하는 결혼식부터 찾는 서비스**

영문 컨셉:

> **Don’t search vendors. Find your taste.**

제품 유형은 일반적인 AI 웨딩플래너보다는

> **AI-native Wedding Visual Discovery Engine**

에 가깝다.

## 4. 기본 사용자 경험

### Step 1. 취향 수집

사용자에게 다양한 웨딩 이미지를 보여준다.

예:

## 5. Wedding Taste Profile

AI가 선택한 이미지들의 공통적인 시각 특성을 분석한다.

예:

### Quiet Modern

- 자연광 선호
- 낮은 채도
- 미니멀한 소품
- 구조적인 실크 드레스
- 과도한 비즈 장식 비선호
- 깨끗한 피부 표현
- 로우번 또는 슬릭 헤어
- 클래식하지만 과하게 전통적이지 않은 분위기

취향을 숫자로 표현할 수도 있다.

예:

- Modern 62%
- Romantic 23%
- Classic 15%

중요한 것은 단순 라벨보다

> **왜 이런 취향으로 판단했는지**

를 사용자가 이해할 수 있게 보여주는 것이다.

---

## 6. 핵심 가치: 취향 → 실제 업체

취향 분석만 하면 재미있는 테스트 앱으로 끝난다.

실제 제품 가치는 다음 단계에서 나온다.

AI가 사용자의 취향과 실제 국내 웨딩 업체 포트폴리오를 비교한다.

예:

### Studio A — 94% Match

추천 이유:

- 자연광 비중이 높음
- neutral tone
- minimal props
- editorial composition
- 사용자가 저장한 사진과 유사한 구도

### Dress Shop B — 91% Match

추천 이유:

- structured silhouette
- silk 중심
- 장식이 적음
- straight neckline 비중 높음

단순히 업체를 추천하는 것이 아니라,

> **“이 업체가 왜 내 취향과 맞는지”**

를 실제 포트폴리오 이미지와 함께 보여준다.

추천 알고리즘보다 **사용자의 피드백 루프**가 중요하다.

## 가격 정보

스드메 가격은 조건과 패키지에 따라 복잡하다.

초기 MVP에서는 가격을 무리하게 해결하지 않아도 된다.

## 범위 확장

처음부터 웨딩 전체를 다루면 데이터와 UX가 급격하게 복잡해진다.

> 20개의 선택으로부터 설명 가능한 취향 프로필과 5개의 추천을 생성한다.

### Outcome C — Product Owner

> 실제 결혼 준비 사용자 10명에게 이 flow를 사용하게 하고 반복적으로 발생하는 불만을 찾는다.

각 owner가 자신의 목표를 달성하기 위해 필요한 코드를 자유롭게 수정한다.

# 9. AI 코딩 에이전트 활용 기본 원칙

코딩 에이전트를 **주니어 개발자처럼 관리하지 않는다.**

좋은 패턴은:

> 인간이 목적과 제약을 설정하고  
> 에이전트가 repository를 탐색하고 구현 방법을 선택하게 한다.

---

## 기본 명령 구조

좋은 요청:

```text
목표:
사용자가 선택한 드레스 이미지를 기반으로 취향 분석 결과를 보여준다.

성공 조건:
- 최소 10개의 이미지 선택
- 결과가 현재 데이터 모델과 호환
- 결과 화면에서 5개의 주요 취향 특성을 표현
- 기존 테스트 유지
- 새로운 동작 테스트 추가

제약:
- 새로운 상태관리 라이브러리를 추가하지 않는다.
- 기존 component pattern을 우선 사용한다.

먼저 repository를 조사하고 관련 구현과 기존 conventions를 파악한 후
필요한 변경을 수행하라.
```

피해야 할 방식:

```text
TasteResult.tsx 만들고
useTaste hook 만들고
API 하나 만들고
Postgres table 추가해.
```

사람이 너무 일찍 구현 방법을 결정하지 않는다.

# 11. One Agent, One Outcome

# 12. Plan은 짧게, 실행은 빠르게

1. 현재 구조
2. 변경할 부분
3. 주요 위험
4. 검증 방법

사람이 확인하고 바로 실행한다.

# 13. AI가 작성한 코드를 사람이 읽는 방식

### 5. 실제 제품에서 실행

가장 중요하다.

# 24. 핵심 운영 철학

AI-native 팀의 장점은 사람이 줄어드는 것이 아니다.

**각 사람이 훨씬 넓은 문제를 독립적으로 해결할 수 있게 되는 것**이다.

따라서 우리가 만들고 싶은 팀은:

> PM이 개발자에게 일을 넘기고  
> frontend가 backend를 기다리고  
> backend가 specification을 기다리는 팀

이 아니다.

세 명 모두 자신의 coding agent를 이용해서 독립적으로 움직이되,

각자가 서로 다른 결과에 대한 책임을 갖는다.

---

## 최종 구조

```text
                     USER / MARKET
                          │
                          │
                 Product / GTM Owner
                  "Should we build it?"
                          │
                  ┌───────┴───────┐
                  │               │
                  │               │
        Experience Owner    Intelligence Owner
        "Can people use it?" "Does it work?"
                  │               │
                  └───────┬───────┘
                          │
                     ONE CODEBASE
                          │
             Claude Code / Codex / Agents
```

### 한 문장으로 정리

> **사람에게 기술 영역을 할당하지 않고 결과를 할당한다.  
> 코딩 에이전트는 각 사람이 그 결과를 독립적으로 만들어낼 수 있게 하는 도구로 사용한다.**

# 3인 AI-Native 팀 업무 분장

## 기본 원칙

세 명 모두 **같은 코드베이스에서 작업**하고, 프론트/백엔드처럼 파일 영역으로 역할을 고정하지 않는다.

각자는 **기술이 아니라 결과를 책임진다.**

### Product / GTM Owner
**“우리가 맞는 걸 만들고 있는가?”**

- 사용자 인터뷰 / 시장 검증
- 제품 범위와 우선순위 결정
- 브랜딩 / 마케팅 / 초기 영업
- 필요하면 코딩 에이전트로 직접 프로토타입, 카피, 랜딩, 간단한 제품 수정

### Experience Owner
**“사람이 실제로 쓰고 좋아하는가?”**

- 전체 사용자 흐름
- UI/UX 및 프론트엔드
- 취향 탐색, 결과, 추천, 저장/공유 경험
- 필요하면 API·DB 등 백엔드도 직접 수정

### Intelligence / Platform Owner
**“제품이 실제로 제대로 작동하는가?”**

- 데이터 모델 / 백엔드 / 인프라
- 이미지 분석 / 취향 모델 / 추천
- AI 모델 연동 및 평가
- 안정성 / 성능 / 비용

---

## 작업 방식

작은 티켓보다 **Outcome 단위**로 일한다.

예:

- Product: 실제 결혼 준비자 10명에게 테스트하고 반복되는 문제를 찾는다.
- Experience: 사용자가 3분 안에 취향 선택부터 결과까지 완료하게 만든다.
- Intelligence: 선택한 이미지로 납득 가능한 취향 분석과 업체 추천 5개를 만든다.

누구든 필요한 파일을 수정할 수 있다.

---

## 코딩 에이전트 사용 원칙

Claude Code / Codex에는 구현 방법을 지나치게 지정하지 않는다.

**목표 + 성공조건 + 제약**을 준다.

예:

> 사용자가 선택한 이미지로 취향 프로필을 생성하고 결과 화면에 보여줘.  
> 기존 구조를 먼저 조사하고 최소한의 변경으로 구현해.  
> 기존 테스트를 유지하고 필요한 테스트를 추가해.

한 agent session에는 가급적 **하나의 outcome**만 맡긴다.

구현 후에는 가능하면 다른 agent로 독립 리뷰한다.

> Claude 구현 → Codex 리뷰 → 수정

---

## 충돌 방지

작업 시작 전에 각자 이것만 공유한다.

> **오늘의 Outcome / 건드릴 가능성이 높은 영역**

파일 ownership을 만들지는 않는다.

---

## 운영 원칙

**main은 항상 동작하게 유지하고, 작은 PR을 자주 merge한다.**

매주 셋이 함께 실제 사용자 반응을 본다.

회의의 핵심 질문은:

> **“이번 주 무엇을 만들었나?”가 아니라  
> “이번 주 실제 사용자에게서 무엇을 새로 알게 됐나?”**

---

> **사람에게 기술 영역을 배정하지 않고 결과를 배정한다. 코딩 에이전트는 각자가 그 결과를 직접 만들어낼 수 있게 하는 도구로 쓴다.**
